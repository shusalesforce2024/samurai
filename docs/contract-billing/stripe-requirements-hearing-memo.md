# Stripe連携 要件確認ヒアリングメモ

## 1. 目的

Stripe × Salesforce連携の要件を固めるため、以下3点を確認する。

| 区分 | 確認したいこと |
|---|---|
| 対象・対象外 | 今回のStripe連携で何を実現し、何を対象外にするか |
| 初期リリース・次フェーズ | 8/10までに入れる範囲と、後続フェーズへ回す範囲 |
| リリース判定 | 本番リリースしてよいと判断する最低条件 |

## 2. ヒアリング対象者

| メンバー | 主な確認観点 |
|---|---|
| 横溝（CTO） | Stripeの利用方針、API、Webhook、システム全体方針 |
| 小室 | 自社サービス側の実装、Stripe API仕様、技術制約 |
| 中山（総務） | 請求、入金確認、返金、freeeとの役割分担 |
| 玉木 | Salesforceでの営業・CS業務、契約更新確認 |
| 高山 | 全社業務設計、システム構成、リリース判断 |
| 加藤 | 収益確認、経営管理、最終判断 |

## 3. タスク1: 要件一覧の対象・対象外を確認する

### 3.1 確認のゴール

今回のStripe連携で「やること」と「やらないこと」を明確にする。

特に、単なる決済URL作成ではなく、Salesforceの契約・請求・入金管理にどこまで組み込むかを確認する。

### 3.2 ヒアリング事項

| No | 確認事項 | 確認相手 | 回答欄 |
|---:|---|---|---|
| 1 | Stripeでは現在、Checkout、Payment Link、Invoice、Subscriptionのどれを使っているか | 横溝、小室 |  |
| 2 | 今回Salesforceから作りたいのは、Checkout決済URLか、Stripe Invoiceか、Payment Linkか | 横溝、小室 |  |
| 3 | Stripe Customerは会社単位か、担当者単位か | 横溝、小室 |  |
| 4 | Salesforce取引先とStripe Customerを1対1で紐づける方針でよいか | 横溝、高山 |  |
| 5 | Salesforce請求 `Invoice__c` とStripe決済を1対1で紐づける方針でよいか | 中山、横溝 |  |
| 6 | Salesforce請求明細をStripe Line Itemへ連携する必要があるか | 中山、小室 |  |
| 7 | Stripe Product / Priceを使うか、Salesforceの商品マスタを正とするか | 横溝、小室 |  |
| 8 | 決済結果はSalesforceへ自動反映する必要があるか | 中山、高山 |  |
| 9 | 返金・取消はSalesforceから実行するか、Stripe画面で実施して結果だけ同期するか | 中山、横溝 |  |
| 10 | 失敗決済・期限切れ決済をSalesforceで確認する必要があるか | 中山、玉木 |  |
| 11 | freee請求書とStripe決済の役割分担はどうするか | 中山、高山 |  |
| 12 | Salesforce上にカード情報を保持しない方針でよいか | 横溝、高山 |  |

### 3.3 対象候補

| 領域 | 対象候補 | 初期判断 |
|---|---|---|
| 顧客 | Salesforce取引先とStripe Customerの紐づけ | 対象 |
| 決済URL | Salesforce請求からStripe Checkout URL作成 | 対象 |
| 請求明細 | Salesforce請求明細をStripe Line Itemへ反映 | 対象 |
| 決済結果 | WebhookでSalesforce請求へ反映 | 対象 |
| ログ | Stripe連携ログ・エラー管理 | 対象 |
| 返金 | Stripe画面で実行し、Salesforceへ結果同期 | 初期は結果同期のみ |
| Subscription | Stripe Billing Subscriptionの本格利用 | 初期対象外候補 |
| メール送信 | Salesforceから決済URLを自動送信 | 初期対象外候補 |
| カード情報 | Salesforceでカード情報を保持 | 対象外 |

## 4. タスク2: 初期リリース対象と次フェーズ対象を分類する

### 4.1 確認のゴール

8/10までに安全にリリースする範囲を決める。

工数・リスク・業務影響を考慮し、初期リリースは「業務で最低限使える」範囲に絞る。

### 4.2 初期リリース候補

| No | 機能 | 初期リリース対象 | 理由 |
|---:|---|---|---|
| 1 | Stripe Customer ID管理 | 対象 | 名寄せの基礎になる |
| 2 | Salesforce請求からCheckout URL作成 | 対象 | 主要業務価値 |
| 3 | 請求明細からLine Item作成 | 対象 | 金額・明細の整合性に必要 |
| 4 | Checkout URL、Session ID、Payment Intent ID保存 | 対象 | 追跡に必要 |
| 5 | Webhook受信 | 対象 | 決済結果自動反映に必要 |
| 6 | Webhook署名検証 | 対象 | セキュリティ上必須 |
| 7 | Stripe Event IDによる二重処理防止 | 対象 | 重複Webhook対策 |
| 8 | 決済成功・失敗・期限切れの反映 | 対象 | 経理確認に必要 |
| 9 | Stripe連携ログ | 対象 | 障害調査に必要 |
| 10 | 未入金・失敗決済リストビュー | 対象 | 経理運用に必要 |
| 11 | 営業・経理・管理者権限 | 対象 | 事故防止に必要 |
| 12 | 業務移行・システム移行・データ移行手順 | 対象 | 本番運用に必要 |

### 4.3 次フェーズ候補

| No | 機能 | 次フェーズ理由 |
|---:|---|---|
| 1 | 名寄せ候補確認LWC | 初期は項目・リストビューで代替可能 |
| 2 | Salesforceからの返金実行 | 金銭操作のため要件・権限・監査設計が重い |
| 3 | Salesforceからの取消実行 | Stripe側状態との整合性設計が必要 |
| 4 | 決済URLのメール自動送信 | 文面・送信者・送信ログ・誤送信対策が必要 |
| 5 | Stripe Billing Subscription本格連携 | 契約更新の正が変わる可能性がある |
| 6 | Customer Portal連携 | 顧客側操作範囲の定義が必要 |
| 7 | Dispute本格管理 | 経理・法務的な運用確認が必要 |
| 8 | 複雑なレポート・ダッシュボード | 初期運用後に実績を見て改善する方がよい |

### 4.4 分類時の判断軸

| 判断軸 | 初期リリースに入れる条件 |
|---|---|
| 業務必須性 | ないとStripe決済運用が成立しない |
| 安全性 | 誤決済・誤紐づけ・二重処理を防ぐために必要 |
| 実装難易度 | 8/10までにテスト込みで完了できる |
| 運用負荷 | 現場が手作業で回避できない |
| 監査性 | 障害時に原因追跡できる |

## 5. タスク3: リリース判定に必要な最低要件を定義する

### 5.1 確認のゴール

本番リリースしてよいかを判断するための最低条件を決める。

### 5.2 リリース判定基準

| No | 判定項目 | 最低条件 | 確認者 | 結果 |
|---:|---|---|---|---|
| 1 | Checkout URL作成 | Salesforce請求からStripe Checkout URLを作成できる | 玉木、小室 |  |
| 2 | 金額整合性 | Salesforce請求明細の金額とStripe Line Itemの金額が一致する | 中山、小室 |  |
| 3 | Customer紐づけ | Salesforce取引先とStripe Customerが正しく紐づく | 横溝、中山 |  |
| 4 | 名寄せ例外 | 複数候補・未解決時に自動で誤紐づけされない | 横溝、小室 |  |
| 5 | 決済成功 | 成功決済がSalesforce請求へ反映される | 中山 |  |
| 6 | 決済失敗 | 失敗決済がSalesforce請求へ反映される | 中山 |  |
| 7 | 期限切れ | 期限切れCheckoutがSalesforceで確認できる | 中山 |  |
| 8 | Webhook重複 | 同じStripe Eventを複数回受けても二重処理されない | 小室 |  |
| 9 | Webhook署名 | 不正なWebhookが処理されない | 小室 |  |
| 10 | 連携ログ | 成功・失敗・エラー内容を確認できる | 小室、川波 |  |
| 11 | 権限 | 営業・経理・管理者で操作範囲が分かれている | 高山 |  |
| 12 | 業務移行 | 営業・経理が新運用手順を理解している | 高山、中山、玉木 |  |
| 13 | システム移行 | 本番設定、Webhook、APIキー、権限設定が完了している | 横溝、小室 |  |
| 14 | データ移行 | 既存Stripe Customer IDの取込・照合方針が確定している | 横溝、中山 |  |
| 15 | 切り戻し | 障害時の切り戻し・暫定運用が決まっている | 高山、横溝 |  |

### 5.3 リリース不可条件

以下のいずれかに該当する場合は、本番リリース不可または条件付きリリースとする。

| No | リリース不可条件 |
|---:|---|
| 1 | 決済金額がSalesforce請求とStripeで一致しない |
| 2 | Stripe Customerの誤紐づけが発生する可能性が残っている |
| 3 | Webhook署名検証が未実装 |
| 4 | Webhook重複時に二重処理される |
| 5 | 決済成功・失敗がSalesforceへ反映されない |
| 6 | APIキーやWebhook Secretの管理方法が決まっていない |
| 7 | 経理が未入金・失敗決済を確認できない |
| 8 | 障害時の暫定運用が決まっていない |

## 7. 初回ヒアリングで必ず聞く質問

1. Stripeでは現在、Checkout、Payment Link、Invoice、Subscriptionのどれを使っていますか。
2. Stripe Customerは会社単位ですか、担当者単位ですか。
3. Salesforce請求とStripe決済は1対1で紐づける方針でよいですか。
4. 商品・価格の正はSalesforce商品マスタですか、Stripe Product / Priceですか。
5. 定期課金はSalesforce側で請求管理しますか、Stripe Subscriptionを正にしますか。
6. 決済成功・失敗・期限切れ・返金をSalesforceでどこまで見たいですか。
7. 返金・取消はSalesforceから実行したいですか、Stripe画面で実施して結果だけ同期しますか。
8. freee請求書とStripe決済の役割分担はどう考えていますか。
9. 既存のStripe Customer / Payment / SubscriptionをSalesforceへ移行・紐づけしたいですか。
10. 8/10リリース時点で、最低限どこまでできていれば業務開始できますか。

## 8. このヒアリングで決めること

| 決定事項 | 決まらない場合の影響 |
|---|---|
| 初期リリース対象 | WBS・工数・テスト範囲が確定しない |
| Stripe決済方式 | API設計が確定しない |
| Customer名寄せ方針 | 誤紐づけリスクが残る |
| Salesforce請求との対応 | 入金管理・レポートが設計できない |
| freeeとの役割分担 | 経理運用が二重管理になる |
| 返金・取消の扱い | 権限・監査・例外処理が確定しない |
| リリース判定基準 | 本番リリース可否を判断できない |
