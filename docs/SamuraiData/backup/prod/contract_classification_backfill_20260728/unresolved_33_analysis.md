## 補完ルール

1. 商品カテゴリ
   - 原則として`Plan__c`と契約名から判定し、freee請求明細がある場合は請求明細を正とする。
   - `CN-00000123`はfreee請求明細から`knock knock AI`。
   - LIXILの着手金契約は契約名から`受託開発`。
2. プランカテゴリ
   - `EN` → `Enterprise`
   - `Pro`、`Pro＋` → `Pro`
   - `BA` → `Basic`
3. アカウント数
   - 原則として、最新年月の契約月次明細の`PeopleNumber__c`を採用。
   - 年払い明細は年数量を12で割り、月当たりのアカウント数へ変換。
   - セキュリティオプション単独契約は、オプション数量ではなく同一取引先の本体契約のアカウント数を継承。

## 残課題

`CN-00000230`は受託開発の着手金契約であるため、`ProductCategory__c=受託開発`は設定可能。一方、`PlanCategory__c`と`AccountCount__c`は非該当である。

推奨は、受託開発では両項目を空欄可とし、未設定エラーとして扱わないこと。プランカテゴリに架空の値を設定したり、アカウント数を0にしたりすると、分析時に実データと区別できなくなるため避ける。

## データ更新方針

- 32件は更新前バックアップを取得したうえで一括更新可能。
- LIXILの1件は商品カテゴリのみ更新し、プランカテゴリ・アカウント数は非該当として空欄を維持。
- 更新後は、32件の3項目一致と、LIXILの例外条件を別々に検証する。
